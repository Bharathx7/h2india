## How to run the staging drills

### 1. Point-in-time restore

1. Note the time T (IST) and make a few changes you can recognise (a test article saved as draft, a test RFQ).
2. Restore into a **new** PostgreSQL container, timing each step. Today (nightly dumps): `pg_restore` the latest dump
   as in `docs/runbooks/deploy.md` (Backups); data since last night is lost. Once WAL archiving is set up: restore
   the base backup and replay the WAL to T − 30 minutes. Then run `pnpm db:migrate` (should find nothing to do).
3. Point a staging copy of the app at it (`DATABASE_URL`), check the recognisable changes are absent and older data is
   present, then switch back.
4. Record: time to restore, data lost (should equal the 30 minutes chosen, never more than the target).

### 2. Kill the worker during a batch

1. Queue a batch: schedule a newsletter test send to 500 test subscribers on staging's Mailpit, or create 200 alert
   matches.
2. While it is sending, `docker kill` the worker container; start it again after 30 seconds.
3. Check in Mailpit and `core.notification_deliveries`: every message arrived exactly once (stable job IDs and
   `core.newsletter_deliveries` make a re-run skip what was sent), and the dead-letter list is empty.

### 4. Email failing for an hour

1. Point `SMTP_HOST` at an address that refuses connections, restart web and worker.
2. Trigger sign-in codes and notifications for an hour. Sign-in codes must show their error at once (security mail
   isn't retried); other mail must wait in `notification_deliveries` as failed with a retry time, and the System
   health panel must show the email adapter as failing.
3. Restore `SMTP_HOST`; the retries must go out once each.

### 6. Payment partner errors

1. With `transactions` on, place an order and choose Pay online.
2. On the simulator choose Bank declines, then Times out, then Stays pending. Each time the order page must show the
   designed state (payment failed / timed out with Try again; pending with "we'll update this page"), the order must
   stay Awaiting payment, and the ledger must not move.
3. Pay successfully on the next try; exactly one payment is recorded.
