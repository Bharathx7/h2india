# Security review, 15 November 2026 (step 12.1)

Branch `step/phase4-hardening`. Measured against OWASP ASVS 4.0, level 2. The threat model for the risky flows is in
`docs/security/threat-model.md`; it refers to the finding IDs below.

## How to read this

- **High**: someone outside the team, or one compromised inbox, can do real harm today. Fix before Launch 1.
- **Medium**: a real weakness, but it needs a second step, or other controls limit it. Fix before Launch 2 (money) or
  record a decision.
- **Low**: hardening. Fix when nearby, or accept in writing.
- **Status**: _Open_ means the code still has the problem. _Fixed in this branch_ means the fix is already in the code
  on `step/phase4-hardening`.

Line numbers are from this branch on 15 Nov 2026.

## High

### H1. A suspended person can still sign in (ASVS 2.1, 3.3, 4.1.3)

**Where**

- `packages/core/src/sign-in/hooks.ts:41-57`: the suspension check runs only for the email-code routes. Line 46 returns
  early for every other route: `if (ctx.path !== SEND && ctx.path !== VERIFY) return;`
- `packages/core/src/sign-in/auth.ts:72-106`: passkey, Google, the Join magic link and the recovery plugin all create
  sessions without that check.
- `packages/core/src/authz/actor.ts:34-77`: `loadActor()` never reads `users.suspended_at`, so a new session gets all
  the person's company and operator permissions.
- `packages/core/src/admin/users.ts:182-210`: `suspendUser()` deletes sessions, which only ends the current ones.

**What is wrong.** Suspending a person (for example for fraud) ends their sessions, but they can sign straight back in
with their passkey, which is the main sign-in method. The same is true for Google, a Join link and a recovery session.
A suspended operator keeps their back-office permissions the same way.

**Fix.**

1. Add `databaseHooks.session.create.before` in `createAuth()` that loads the user and throws the
   `SIGN_IN_ERROR.suspended` error when `suspendedAt` is set. This covers every sign-in method in one place.
2. Make `loadActor()` return `VISITOR` (no companies, no operator permissions) when the user is suspended, so an old
   cookie or a missed path still gets nothing.
3. Add an integration test per sign-in method (code, passkey, magic link, recovery) that a suspended user is refused.

**Status.** Fixed in this branch: `loadActor()` returns a visitor for a suspended person (`packages/core/src/authz/actor.ts`), and Better Auth's `databaseHooks.session.create.before` refuses any new session for them (`packages/core/src/sign-in/auth.ts`). Test: `packages/core/src/authz/gate.int.test.ts`.

### H2. Operators can use the back office with an email code alone (ASVS 2.2.1, 4.3.1)

**Where**

- `apps/web/src/admin/shell.tsx:18-25`: `requireOperator()` checks the session and the permission only.
- `packages/core/src/sign-in/auth.ts:76-91`: an email code is a full sign-in method for every account.
- Decision A172 (4): "Every operator uses a passkey." Nothing in the code enforces it.

**What is wrong.** Whoever reads an operator's inbox can sign in as that operator. Operators can approve account
recovery for any company whose only admin lost access (`recovery/recovery.ts:419-421`), approve company claims, grant
the Verified badge, start View as, and propose money switches. One phished mailbox is enough.

**Fix.** Require a passkey sign-in for operator areas. For example, record in the session how the person signed in
(the passkey hook at `hooks.ts:104-108` already sees it), and make `requireOperator()` and `operatorSession()` refuse a
session that did not come from a passkey, with a page that asks the operator to sign in with their passkey. Keep the
email code for ordinary members. Add a browser test.

**Status.** Fixed in this branch, decision A181 to confirm: passkey sign-ins mark their session (`sign-in/step-up.ts`, `hooks.ts`); with `operatorPasskey` on (default in production) the web app's gate drops operator permissions in any other session (`setOperatorGate`, `apps/web/src/server/auth.ts`), and `requireOperator()` sends the operator to `/sign-in/passkey`. Test: `packages/core/src/authz/gate.int.test.ts`.

## Medium

### M1. The Content Security Policy allows inline scripts (ASVS 14.4.3, 5.3.3). Decision A180

**Where.** `apps/web/src/security/headers.ts:29-56` (`script-src 'self' 'unsafe-inline'`), applied to every response
in `apps/web/src/proxy.ts:29-45`.

**What is wrong.** With `'unsafe-inline'`, the policy does not stop an injected inline script. It still blocks scripts
from other sites, framing, plugins, foreign form targets and `<base>` tricks, so it is useful, but it is not the main
XSS defence it could be. No XSS was found in this review (see "Checked, fine"); this is defence in depth.

**Why it is like this.** Most public pages are pre-rendered. A per-request nonce makes every page dynamic, which costs
server time and the CDN cache.

**Options for the founder (A180).**

1. Keep `'unsafe-inline'` and accept the risk (the current state).
2. Nonces with `'strict-dynamic'` on signed-in areas only (workspaces, admin, checkout), which are dynamic already, and
   keep the static public pages as they are. This protects the pages that hold money and personal data.
3. Nonces everywhere; measure the cost first.

The reviewer recommends option 2.

**Status.** Open, decision A180.

### M2. The bank-change step-up can be met by a passkey the attacker just added (ASVS 2.5, 2.7, 4.2)

**Where**

- `packages/core/src/sign-in/hooks.ts:104-108` and `packages/core/src/sign-in/step-up.ts:10-16`: any passkey sign-in
  records the step-up, whatever the age of the passkey.
- `packages/core/src/supplier/bank.ts:187-189`: `confirmBankAccount()` accepts that step-up.
- `apps/web/src/app/(app)/(auth)/sign-in/SignInFlow.tsx:254`: a signed-in person can add a passkey; there is no
  notice to the person or to other admins when a passkey is added (no template for it in
  `packages/emails/src/registry.ts`).
- `packages/core/src/sign-in/auth.ts:104`: `userVerification: "preferred"`, so a security key touched without its PIN
  also counts.

**What is wrong.** The chain "read the admin's inbox → sign in with an email code → add a passkey → sign in with it →
change the payout bank account" works. The 72-hour hold and the email and SMS notices to every admin
(`bank.ts:229-281`) are what stop the money leaving. If the company has one admin, the email notice goes to the
attacker's inbox and only the SMS (sent only to a verified mobile) warns the real owner.

**Fix.**

1. Count a passkey for step-up only if it was registered more than 24 hours earlier (or before the current session).
2. Send a security notice (email and SMS, cannot be turned off) when a passkey is added, to the person and to the
   company's other admins.
3. Use `userVerification: "required"` for the step-up.
4. Consider making the hold longer when the person's last passkey was added recently.

**Status.** Open.

### M3. AUTH_SECRET is the root of every key (ASVS 6.4.1, 6.4.2)

**Where.** The same secret, `AUTH_SECRET`, signs sessions (`sign-in/auth.ts:37`) and derives:

- the payout bank account encryption key, `supplier/bank.ts:30`;
- the worker's internal key, `internal.ts:6-8`;
- the simulated partner's webhook key, `adapters/payments/sim.ts:20`;
- Payload's secret, `apps/web/src/payload.config.ts:70`;
- token hashing for Join and recovery (`companies/drafts.ts:17`), newsletter and alert links, webinar links.

**What is wrong.** A leak of this one value breaks everything at once. Worse, the response to a leak (rotate it, as
`docs/secrets.md:30` says) would make every stored bank account number unreadable, because the encryption key is
derived from it and the cipher text has no key version.

**Fix.** Add a separate `BANK_DATA_KEY` (32 random bytes) with a key ID written at the start of each cipher, so old
rows can be re-encrypted after a rotation. Give the internal jobs key and the payment webhook key their own settings
too. Write the rotation steps in `docs/secrets.md`.

**Status.** Open.

### M4. A suspended company keeps working and keeps being paid (ASVS 4.1.3; business logic)

**Where**

- `packages/core/src/admin/users.ts:236-266`: `suspendCompany()` hides the listings only.
- `packages/core/src/authz/actor.ts:47`: `loadActor()` filters out deleted companies but not suspended ones.
- `packages/core/src/orders/money.ts:585-600`: `runPayouts()` pays every supplier with an Active account and no hold;
  it does not check `organisations.suspended_at`.

**What is wrong.** If a supplier is suspended for fraud, its people can still change the bank account, answer orders
and receive payouts at the next run.

**Fix.** Skip suspended suppliers in `runPayouts()` (and show "Payout held: company suspended" to Finance). Decide
with the founder what a suspended company may still do (G10): at least no bank changes, no new quotes, no payouts.
Enforce it in core, not in pages.

**Status.** Partly fixed in this branch: `runPayouts()` skips a suspended supplier until the suspension is lifted (test in `orders.int.test.ts`). What else a suspended company may still do (read its orders, appeal) needs the G10 decision.

### M5. The CMS API relies on SameSite cookies against cross-site requests (ASVS 4.2.2, 13.2.3)

**Where**

- `apps/web/src/cms/auth-strategy.ts:52-58`: the Payload strategy accepts our session cookie for every request, with
  no check of `Origin` or `Sec-Fetch-Site`.
- `apps/web/src/payload.config.ts:67-70`: no `csrf` or `cors` setting.
- `infra/nginx/h2india.conf:4-6, 65`: the admin domain serves `/api/cms`. The admin and public domains are both under
  `deecodes.io`.

**What is wrong.** Server actions are protected by Next.js's own origin check, and Better Auth checks origins on its
routes. The CMS REST API has neither. The session cookie is `SameSite=Lax`, which stops other websites, but not other
sites under `deecodes.io` (they count as the same site). Any page that can run script on another `deecodes.io`
subdomain could send a form post to `/api/cms/...` with the editor's cookie. Payload accepts form posts with a
`_payload` field (`payload/dist/utilities/addDataAndFileToRequest.js:51-52` in 3.93.0), so this is likely to work; confirm it with a test.

**Fix.** In `h2indiaStrategy.authenticate`, return no user for a non-GET request unless `Origin` equals the admin
`APP_URL` (or `Sec-Fetch-Site` is `same-origin`). Add a browser test that a cross-origin form post to `/api/cms` is
refused. Longer term, put H2 India on its own registrable domain (see Accepted risks).

**Status.** Open.

### M6. The app uses the PostgreSQL superuser; the audit log's guard can be removed (ASVS 1.4.3, 7.3.3, 14.1)

**Where**

- `infra/h2india.env.example:21-24` and `infra/compose.prod.yml:58`: the app's `DATABASE_URL` uses `POSTGRES_USER`,
  which the official image makes a superuser.
- `packages/db/migrations/0001_audit_append_only.sql` and `0008_audit_retention.sql`: the audit log is append-only
  through a trigger.

**What is wrong.** A superuser can disable or drop the trigger and change the log. A superuser can also run
`COPY ... TO PROGRAM`, which turns any future SQL injection into control of the database container. No SQL injection
was found (see "Checked, fine"); this is about limiting damage.

**Fix.** Run migrations as the owner role, and run the web app and the worker as a separate login role that can only
read and write the tables (no `ALTER`, no `TRIGGER`, no superuser). Copy the audit log nightly to write-once storage
(or add a hash chain) so tampering is detectable.

**Status.** Open.

## Low

### L1. Google sign-in links to any existing account with the same email (ASVS 2.5)

`packages/core/src/sign-in/auth.ts:72`: `accountLinking: { enabled: true, trustedProviders: ["google"] }`. A Google
account for the same address is linked without asking. A company's Google Workspace administrator can therefore sign
in as any of its staff on H2 India. This is normal for "Sign in with Google", but it is a second way in that does not
go through the per-email code limits. **Fix:** notify the person when a Google account is linked; or link only after
an email code. **Status:** Open.

### L2. Delivery link details (ASVS 2.7, 6.2)

`packages/core/src/orders/flow.ts`:

- line 906: the link token is 8 random bytes (64 bits). 16 bytes is the usual minimum.
- line 931: the link and the code go in the same SMS, so the code proves nothing beyond having the SMS.
- line 915: the code hash is plain SHA-256 of `orderId:code`; with the database, the 6-digit code is found at once.
- line 745: links live 14 days.

The lockout after five wrong codes works (`flow.ts:1076-1095`, locked under a row lock), and a confirmed receipt does
not release money (the buyer still accepts). **Fix:** 16-byte token; HMAC the code with a server key; shorten the link
to 7 days; consider sending the code in a second SMS or asking for it from the delivery driver. **Status:** Open.

### L3. Two GET routes change data (ASVS 4.2.2, 13.1)

- `apps/web/src/app/(app)/(site)/cart/add/route.ts:8-29` adds to (and with `replace=1` empties) the cart on GET, with
  no `Sec-Fetch-Site` check. A link on another site can change a buyer's cart (only while `transactions` is on).
- `apps/web/src/app/(app)/(site)/opportunities/jobs/[slug]/apply/route.ts:12-21` records a job application on GET.

Both also slip past the View as write block, which only refuses POST, PUT, PATCH and DELETE
(`apps/web/src/proxy.ts:53`): an operator viewing as someone who clicks Apply writes to that person's account.
**Fix:** check `Sec-Fetch-Site` as `sign-out/route.ts:8-10` does, and skip the write when the View as cookie is set.
**Status:** Open.

### L4. Payment webhook cross-checks (ASVS 13.2, 11.1)

`packages/core/src/orders/money.ts`:

- line 322: the payment found by `partnerPaymentId` is not checked to belong to the order named in the event
  (`orderRef`); the amount in the event replaces the checkout amount (line 326).
- `packages/core/src/adapters/payments/sim.ts:115-120`: the signature covers the body only, without a timestamp.
  Replays are stopped by the unique event ID (`money.ts:141-151`), which is enough for the simulator.

**Fix (with the real partner, M3):** refuse or flag an event whose payment belongs to another order or whose amount
differs from the checkout; check the partner's timestamp header with a 5-minute tolerance. **Status:** Open.

### L5. The bot challenge fails open (ASVS 11.1.4)

`packages/core/src/protect.ts:60-63` lets the form through when the challenge provider is unreachable. This is a
deliberate choice so people are not blocked; per-IP limits still apply. **Fix:** none needed; record the acceptance
when the provider is chosen. **Status:** Open (accept).

### L6. The GSTIN check has no rate limit (ASVS 11.1.4, 13.2)

`apps/web/src/app/api/v1/organisations/gstin-check/route.ts:7-17` and `packages/core/src/companies/check.ts:25-38`.
Any signed-in person can check GSTINs without limit and learn the company ID and member count of a registered one.
When the real provider (M4) charges per lookup, this becomes a cost risk. **Fix:** `hitThrottle` per user (for example
30 an hour) and per IP. **Status:** Open.

### L7. CI pins by tag (ASVS 14.2.4)

`.github/workflows/ci.yml:59-127`, `codeql.yml:26-37`, `image.yml:44-46` use `@v7`-style tags; `image.yml` runs
`aquasec/trivy:0.57.1` by tag (the comment there already says to pin by digest). A moved tag runs someone else's code
with access to the image push token. **Fix:** pin every action by commit SHA and Trivy by digest; Dependabot
(`.github/dependabot.yml`) keeps them up to date. **Status:** Open.

### L8. Session length (ASVS 3.3.2, 3.3.4)

`packages/core/src/sign-in/rules.ts:11` and `auth.ts:60`: 7 days, refreshed daily, for everyone. There is no idle
timeout and no shorter session for operators. **Fix:** a shorter session for operator sign-ins (for example 12 hours)
once H2 is done. **Status:** Open (decision).

### L9. Recovery approval after expiry (ASVS 2.5.6)

`packages/core/src/recovery/recovery.ts:405-438`: `decideRecovery()` reads the request without checking
`expiresAt`, and `applyMobileChange()` (line 361-366) updates without checking the status is still waiting. Two admins
answering at once could both apply. **Fix:** put `status` and `expires_at > now()` in the update's WHERE and refuse when
no row changes. **Status:** Open.

### L10. /cms script policy (ASVS 14.4.3)

`apps/web/src/security/headers.ts:26-34`: on `/cms` only, `'unsafe-eval'` and `https://cdn.jsdelivr.net` are allowed
for Payload's code editor. jsDelivr serves any npm package, so this adds little protection there. Operators only.
**Fix:** part of A180; self-host the editor's files if Payload allows. **Status:** Open (part of A180).

## Checked, fine

- **Open redirects.** `safeReturnPath()` (`sign-in/rules.ts:34-50`) refuses `//`, `/\`, control characters and
  anything that resolves to another origin. Other redirects use fixed paths or IDs checked with a pattern
  (`api/view-as/end/route.ts:16-17`). The job Apply redirect goes to the job's own address, which an editor approves.
- **SQL injection.** No `sql.raw` or string-built SQL outside migrations. Every `${...}` inside a `sql` template is a
  bound parameter. Search filters quote values with `JSON.stringify` (`alerts/rules.ts:101`, `search/query.ts:180`).
- **XSS.** The only `dangerouslySetInnerHTML` uses are JSON-LD, each with `<` escaped (`seo/jsonld.tsx:13`,
  `news/article.tsx:512-515`, `opportunities/jobs/[slug]/page.tsx:58`). Rich text renders through React, which blocks
  `javascript:` links. CMS images refuse SVG (`cms/collections/Media.ts:6, 15`).
- **SSRF.** The server fetches only addresses from settings (`protect.ts:49`, `internal.ts:20`). No server code fetches
  a user-given URL; uploads go straight from the browser to storage.
- **Files.** Signed upload links fix type and size (`files/storage.ts:37-45`); the worker scans with ClamAV and fails
  closed (`files/clamav.ts:4-5`), sniffs the real type, re-encodes images and only then marks the file Available
  (`files/files.ts:334-408`). Downloads need `canRead` and give a 5-minute link with `no-store`
  (`files/files.ts:411-452`). nginx gives file paths nosniff and a script-blocking, sandboxed CSP
  (`infra/nginx/h2india.conf:33-43`). Per-user and per-IP upload limits (`files/files.ts:111-114`).
- **Authorisation.** `can()` refuses company permissions without a company (`authz/can.ts:23-28`); `inScope()` returns
  `false` for an empty scope (`authz/scope.ts:32-36`). Bank, orders and files all filter by company.
- **Internal API.** HMAC key compared in constant time (`internal.ts:10-15`); nginx returns 404 for `/api/internal/` on
  both domains (`h2india.conf:27, 62`); app ports listen on 127.0.0.1 only (`compose.prod.yml:25, 34`).
- **Test pages and the simulated partner.** `/dev` returns 404 unless in development or `FLAG_DEV_PAGES=true`
  (`(dev)/dev/layout.tsx:13`), and the pay action checks again and checks the buyer (`dev/pay/[paymentId]/actions.ts:16-24`).
  `devPages` cannot be switched from System settings (`config/src/flags.ts:50-58`). The simulated partner refuses to
  start in production unless `PAYMENT_SIM_ALLOWED=true` (`adapters/payments/index.ts:19-23`). Keep both off in
  production.
- **Payment webhook.** Signature checked in constant time before parsing (`sim.ts:115-120`, `money.ts:137`); each event
  is stored once by ID and processed once under a row lock (`money.ts:141-180`); ledger postings carry the event ID.
- **Payouts and the bank hold.** The account number is encrypted (AES-256-GCM) and never leaves `bank.ts`; payouts skip
  a company with a change on hold (`money.ts:597-600`); there is no way to shorten a hold; any admin can cancel.
- **Delivery code.** Five wrong codes lock the link, counted under a row lock (`flow.ts:1068-1095`); a used or expired
  link is refused; the code is never shown to the supplier (`supplier/orders/actions.ts:27-37`); public form limits
  apply (`delivery/actions.ts:29-31`). See L2 for the details to tighten.
- **Sign-in limits.** Per-email pause after 5 wrong codes, 5 codes an hour, 30 seconds between codes, with atomic
  counters (`sign-in/hooks.ts`, `sign-in/throttle.ts`); per-IP limits in Better Auth (`auth.ts:62-71`). The IP header
  is written by nginx and cannot be faked (`h2india-proxy.conf:3-4`, `h2india.env.example:17`). Codes are stored hashed.
- **Account recovery.** Two proofs on every path; recovery codes compared in constant time with a per-destination pause
  (`recovery/codes.ts:79-107`); recovery sign-in works once (`recovery.ts:204-209`). See L9.
- **View as.** The cookie is httpOnly and bound to the operator's own grant (`admin/users.ts:310-320`); admin screens
  use the operator's real session; the proxy refuses writes (`proxy.ts:53-58`). See L3 for GET writes.
- **CSRF.** Server actions get Next.js's origin check; Better Auth checks origins; cookies are `SameSite=Lax`; sign-out
  checks `Sec-Fetch-Site`. See M5 for the CMS API and L3 for GET writes.
- **Secrets.** Settings are typed and checked at start (`packages/config/src/env.ts`); only `NEXT_PUBLIC_*` values reach
  the browser. Gitleaks runs in CI. No `.env` file other than `.env.example` was read for this review.
- **Dependencies.** `pnpm audit --audit-level high` and gitleaks in CI; Dependabot weekly; pnpm only runs install
  scripts for the listed packages (`pnpm-workspace.yaml:5-9`). The audit was not re-run for this review (no network);
  CI is the source of truth.

## Accepted risks need a written decision

Only the founder can accept these. Each needs an entry in `docs/decisions.md`.

1. **Inline scripts in the CSP** (M1, L10): decision A180.
2. **The email inbox is the root of every account.** An email code signs anyone in (ADR 0003). Recovery and the bank
   step-up add checks, but whoever controls a person's mailbox controls their account until H2 and M2 are fixed.
3. **Recovery approved by support** when the person is their company's only admin (A17): a single operator decides,
   with no second person.
4. **No automatic acceptance of deliveries** (G13 default): a buyer who never accepts a good delivery holds the
   supplier's money until a dispute or an operator decides.
5. **A proof of delivery is any uploaded file.** The supplier's upload moves the order to Delivered; the buyer and the
   receiving contact are the check.
